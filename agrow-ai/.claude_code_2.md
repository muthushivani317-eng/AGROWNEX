# AgrowAI — Farmer-Grade App Excellence Prompt (Claude Code, Part 2)

Run AFTER the production-hardening prompt (Phases 1–6). Same repo root.
This prompt is about the farmer, not the reviewer: a 55-year-old smallholder
in Thoothukudi district, low literacy, ₹8,000 Android phone with 2–3 GB RAM,
patchy 3G, paying for every megabyte. Every change below is judged by one
question: does this help a real farmer keep more of their harvest and income?

Work in phases, IN ORDER. After each phase run the test suites, add tests for
what you built, and commit before moving on.

## PHASE 7 — Measurement (do this first; we are flying blind)
- Add a privacy-respecting analytics layer in `agrow-ai/` behind a provider
  seam (`AnalyticsProvider` Protocol; PostHog self-hosted or Firebase
  Analytics as the concrete impl, plus a no-op mock for dev). Never send
  photos, phone numbers, or free-text farmer questions to analytics.
- Instrument the funnel with named events: app_open, onboarding_step_viewed,
  onboarding_completed, first_scan_started, first_scan_result, scan_repeat,
  weather_viewed, market_price_viewed, chat_message_sent, voice_message_sent,
  notification_opened, session_end. Include days_since_install on every event.
- Backend: a lightweight `POST /api/v1/events` ingest endpoint (rate-limited,
  authenticated) writing to an `analytics_events` table, so we own the data
  even if the vendor changes.
- Build an admin dashboard route (`/api/v1/admin/retention`) returning D1/D7/
  D14/D30 retention, activation rate (% reaching first scan result), and
  feature usage counts — segmented by village/block so we can see which KVK
  cohorts stick.
- Add crash + error reporting to the mobile app (Sentry React Native), with a
  crash-free-sessions target of ≥99.5%.

## PHASE 8 — Onboarding: value before friction
- Restructure the first-run flow so the farmer reaches value in under 30
  seconds and ZERO reading beyond a Tamil sentence: launch → Tamil/English
  toggle (big icons, spoken audio prompt) → immediate "photo of your leaf"
  camera CTA → diagnosis result → ONLY THEN ask for phone/OTP to save it.
  Support a guest/anonymous session server-side (device-scoped token) that is
  merged into the real account on OTP verification. New migration if needed.
- Reduce complete-profile to two optional fields (district, primary crop);
  everything else moves to a progressive "improve my advice" prompt later.
- Every onboarding screen must have: a spoken Tamil audio prompt (TTS seam
  from Phase 5), icon-first UI, minimum 56dp touch targets, and text at
  ≥18sp. Assume the user cannot read confidently.
- Add a 60-second Tamil "how to take a good leaf photo" illustrated guide
  (static images + audio, no video — data cost).
- Test: an onboarding integration test asserting number of taps and screens
  to first diagnosis result is ≤4 taps.

## PHASE 9 — Low-end device & low-bandwidth performance
- Compress images client-side before upload: resize longest edge to 1280px,
  JPEG quality ~75, target <500KB. Show the farmer the estimated data cost
  saved. Never upload the raw camera file.
- Add an upload queue (MMKV-persisted) with automatic retry on reconnect;
  the farmer can take a photo with no signal and it sends later. Show clear
  Tamil status: waiting / sending / done.
- Offline-first reads: cache last weather bundle, last 30 days of market
  prices, and all past diagnoses in expo-sqlite. Every screen must render
  useful content with zero network, with a clear "last updated" timestamp in
  Tamil. Never show a blank screen or an infinite spinner.
- Performance budget, enforced in CI where possible: APK ≤30MB, cold start
  ≤3s on a low-end device, no screen exceeding 16ms frame budget during
  scroll. Enable Hermes, remove unused deps, lazy-load heavy routes, replace
  any full-list renders with FlashList/virtualization.
- Add a "low data mode" toggle (default ON): skips satellite imagery, uses
  text-only weather, more aggressive caching.

## PHASE 10 — Trust, safety and Indian data law (DPDP Act 2023)
- Tamil-first consent screen at first launch: what we collect (phone, coarse
  location, crop photos), why, how long we keep it, and who it is shared with
  (nobody). Explicit opt-in, logged with timestamp and version.
- Implement a real `DELETE /api/v1/farmers/me` that hard-deletes profile,
  photos (from R2), diagnoses, chats and analytics identifiers within 30 days,
  plus an in-app "delete my data" button in Tamil. Test that it actually
  deletes — including object storage.
- Data export endpoint (farmer's own data, JSON) — required by DPDP.
- Publish `PRIVACY_POLICY.md` (Tamil + English) and link it in-app; required
  for Play Store and App Store submission.
- Safety surface in the UI: every diagnosis shows confidence, and any result
  with `needs_expert_review=true` shows a prominent Tamil banner ("இது உறுதி
  இல்லை — நிபுணரிடம் கேளுங்கள்") with a one-tap link to the experts module.
  Banned-pesticide warnings render in high-contrast red with an icon.
  Never render a commercial brand name — add a render-time guard and a test.

## PHASE 11 — Retention loop (the app must earn the next open)
- Daily Tamil push notification worth opening: one useful line combining
  weather + crop stage + one action ("நாளை மழை — இன்று தெளிப்பு வேண்டாம்").
  Personalized from the existing farm-memory context. Frequency-capped at 1/day,
  farmer-configurable, easy to mute (never spam — a muted farmer is a lost one).
- Price alerts: farmer sets a target price for their crop; notify when the
  nearby mandi crosses it. This is the single most monetizable habit we can
  build — it directly protects income.
- Crop calendar reminders tied to the farm's sowing date (sow → fertilize →
  irrigate → harvest), delivered as Tamil push + voice.
- A weekly "your farm this week" summary card: scans done, weather ahead,
  best mandi price nearby. Cheap to build, strong D7 driver.
- Instrument all of the above with the Phase 7 events so we can kill whatever
  doesn't move retention.

## PHASE 12 — KVK / extension-officer surface (our distribution channel)
- Add an `extension_officer` role (extend the existing RBAC models) with:
  bulk farmer onboarding via a single-scan QR code at a KVK training session
  (deep link → pre-filled block/village → OTP), a roster of farmers they
  onboarded, and a village-level dashboard: recent disease reports, emerging
  pest clusters (simple geo-clustering over existing diagnoses), and crops at
  risk this week.
- Officer broadcast: send a Tamil advisory to all farmers in a block (reuses
  the notification provider; rate-limited, audited).
- Exportable KVK impact report (PDF/CSV): farmers onboarded, scans performed,
  top diseases detected, advisories sent — this is what the dean shows at
  review meetings, and it is why the KVK keeps promoting us.
- Everything here reuses existing modules; do not fork logic.

## PHASE 13 — Store readiness
- Play Store + App Store assets: Tamil-first store listing copy, screenshots
  in Tamil, data-safety form answers consistent with PHASE 10, target API
  level current, signed release build via EAS. Document the whole release
  process in `RELEASE.md`.
- Accessibility pass: TalkBack/VoiceOver labels in Tamil on every interactive
  element, contrast ratios ≥4.5:1, dynamic type support.
- Final: update `README.md` and `UPGRADE_REPORT.md` with what is now live vs
  seam-only. Accuracy over ambition — never claim a feature we have not shipped.

Guiding rule for every ambiguous decision: choose what protects the farmer's
crop, money, and data — in that order. A farmer who cannot read must still be
able to use every core feature. If a feature cannot be explained in one spoken
Tamil sentence, it is too complicated to ship.
