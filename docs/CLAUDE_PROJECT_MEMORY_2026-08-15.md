## 2. Product purpose and non-negotiable principles

AgrowAI is a Tamil-first agricultural application for farmers in Tamil Nadu. Its purpose is to provide useful daily workflows while preserving farmer safety, data honesty, and controlled release boundaries.

Product principles:

1. Tamil-first, with English parity.
2. Farmers must never be asked to pay inside these advisory workflows.
3. Never fabricate weather, satellite, flood, soil, disease, nutrient, stage, harvest, market, scheme, storage, provider, or expert results.
4. Missing credentials or evidence must produce an explicit unavailable or insufficient-data state, never a production mock.
5. Model confidence is not agronomic certainty.
6. Farmer confirmation is farmer evidence, not expert verification.
7. Completing an action is not proof of agronomic success.
8. Unverified crop calendars, stage rules, disease-risk rules, readiness criteria, and agronomic recommendations remain disabled.
9. No pesticide brand, chemical brand, dosage, or treatment may be generated by an AI provider or silently introduced by code.
10. General-farmer disease inference remains fail-closed until field evidence and promotion gates are satisfied.

## 4. Overall architecture

### Mobile

The mobile app uses React Native with Expo Router and TypeScript. Major patterns are:

- Route groups for authentication and authenticated tabs.
- Zustand for authentication/session state and selected workflow state.
- TanStack Query for server state, refetching, and mutation workflows.
- Provider interfaces separating API providers from explicitly local/development providers.
- MMKV/SecureStore-based persistence, with tokens in secure storage and non-secret profile/session metadata in application storage.
- Tamil and English locale maps under `agrow-ai/localization/locales`.
- Shared design components under `agrow-ai/components/ui`.
- Feature modules under `agrow-ai/features/<feature>` containing screens, hooks, providers, mappers, storage, types, and tests.

### Backend

The backend uses FastAPI, Pydantic, SQLAlchemy async models/repositories/services, and Alembic migrations.

The standard backend flow is:

`router -> authenticated dependency -> service -> repository/provider -> database or external service -> typed response`

Common backend rules:

- Thin routers; business decisions belong in services/engines.
- Firebase ID tokens are verified through Firebase Admin.
- Ownership and controlled-role checks occur server-side.
- External providers have explicit unavailable/error outcomes.
- Production mocks require explicit development/test policy and must not be silently selected.
- HTTP failures use stable, sanitized error codes.
- Images are validated server-side before provider/model calls.

### Provider boundary

Features that depend on external systems use provider abstractions. Production providers may use Open-Meteo, Firebase, OpenAI, Gemini, Copernicus, Cloudflare R2, or other configured services. Mock providers are fixtures for tests or explicit development only. Missing production configuration fails closed.

## 5. Startup, navigation, localization, and offline behavior

The app starts through `app/index.tsx` and the startup state machine. It bootstraps secure storage, restores session and language state, validates release configuration, and resolves the correct route. Recoverable startup failures render an explicit retry/reset screen rather than a blank screen.

Navigation preserves existing Expo Router architecture. Authentication screens live in `app/(auth)`. Authenticated feature entries are routed through the tab/home structure and feature-specific screens.

Tamil is the primary product language. English keys must remain in parity. UI error codes are mapped to safe localized messages rather than exposing backend details.

Offline architecture varies by feature:

- Read-only cached results remain labelled with their original timestamp and source.
- Queued farmer actions expose pending-sync state.
- Stale or cached evidence is never presented as live.
- Security-critical capability data fails closed when stale or unavailable.

## 6. Authentication: real Firebase phone OTP

### What was built

The mobile implementation uses `@react-native-firebase/auth`, not the Firebase browser SDK. The real phone flow is:

`phone input -> Indian E.164 normalization -> signInWithPhoneNumber -> Firebase confirmation -> six-digit OTP -> confirmation.confirm -> Firebase user -> getIdTokenResult -> backend /auth/otp/verify -> local authenticated session`

Relevant mobile files include:

- `features/auth/services/firebaseAuthProvider.ts`
- `features/auth/services/authProvider.ts`
- `features/auth/hooks/useAuthActions.ts`
- `features/auth/store/authStore.ts`
- `features/auth/screens/LoginScreen.tsx`
- `features/auth/screens/VerifyOtpScreen.tsx`
- `features/auth/phone.ts`

The KVK build selects real Firebase when configured. If Firebase configuration is absent, production, internal-testing, and KVK profiles select an unavailable provider. They do not fall back to test login. A development mock with an environment-supplied OTP remains available only for explicit development/tests.

The login screen now distinguishes a development mock from a release Firebase-unavailable state, eliminating misleading “development test verification” wording in KVK builds.

Phone numbers are normalized to Indian E.164 form (`+91` followed by a valid ten-digit Indian mobile number). Invalid numbers are rejected before Firebase invocation.

The OTP screen provides six visible input positions, keyboard handling, verify loading state, a bounded resend timer, resend replacement of confirmation state, invalid/expired/network error messages, and change-number navigation.

### Backend verification

The backend `verify_id_token` path uses Firebase Admin with signature, issuer, audience, expiry, revocation, and disabled-user checks. Missing, invalid, expired, or revoked tokens fail with sanitized 401 errors. On successful `/auth/otp/verify`, the backend creates or finds the Firebase UID user, assigns the farmer role, records login/session history, issues a rotating server refresh token, and returns profile/session state.

### Current limitation

The native wiring, configuration files, package match, automated tests, secure APK build, and backend verification are complete. Real SMS send/receipt, real OTP verification, Firebase Console signing registration, and real backend acceptance were not validated for the latest APK because no authorized Android device was attached. Therefore field-test authentication readiness remains NO until that physical chain passes.

## 7. Farms, ownership, profiles, and team controls

Farm records are the ownership anchor for weather, satellite, soil, growth, stage, readiness, action, disease, and nutrient workflows. Backend dependencies enforce current-user ownership on reads and writes. Team access is a separate controlled feature with explicit roles rather than implicit access.

Profiles store farmer language and farm context. Session logout clears tokens and cached query data. User switching is tested so a new user does not inherit the previous farmer's protected state.

Approximate location must not be converted into a verified farm boundary. AOI-dependent features require a stored, valid farm polygon.

## 8. Weather-to-Action Engine

### Purpose

Weather-to-Action is intended as AgrowAI's primary daily-use feature. It converts observable weather forecast conditions into a cautious mission/note without changing the Open-Meteo pipeline.

### How it works

1. The app obtains a farm/location context.
2. The backend fetches Open-Meteo current/hourly/daily data.
3. Existing cache behavior stores weather responses with timestamps.
4. The weather mission engine evaluates the existing deterministic weather conditions.
5. The response explains the action, causing weather condition, forecast timing, reliability, and whether data is live, cached, or stale.
6. Missing or unreliable data produces a cautious unavailable/verification message instead of an instruction.

### Safety

- No new agronomic thresholds were invented during refinement.
- Weather is evidence, not automatic authority for pesticide, irrigation, or chemical instructions.
- Any agronomic rule without documented expert verification must be presented as requiring official/expert verification.
- Cached and stale data are labelled and cannot masquerade as live.

Key backend areas include `app/modules/weather`, especially `service.py`, `insights.py`, `mission.py`, and `action_source.py`. Mobile code is under `features/weather`.

## 9. Crop identification and disease detection

### Crop confirmation and capability control

Disease analysis starts with crop identification or farmer selection. A server-generated confirmation receipt binds the actor, image hash, identified/confirmed crop, expiry, and one-time token. Tokens cannot be replayed, transferred across users, used for another crop, or reused with another image.

The authenticated `/disease/capabilities` endpoint is the server authority for what the current user may see and invoke. It returns crop readiness, integrity, adapter availability, release scope, authorization, supported classes, and stable unavailable reasons. Mobile treats unknown/malformed/stale capability data as blocked.

Controlled roles include internal tester, pilot tester, and KVK reviewer according to each crop's registry policy. General-farmer inference is blocked.

### Models

The repository contains crop-specific runtime paths for banana, paddy, cotton, groundnut, chilli, and redgram, plus crop-identification and safety gates. Model bundles are verified by artifact hashes and runtime readiness. Advertised runtimes are inventoried and prewarmed/cached so capability reads do not repeatedly load/hash large models.

### Image safety and abstention

Before inference, the backend applies upload type/size/decode checks, dimensions, crop/OOD/quality gates, and confirmation-token validation. Low quality, wrong crop, unsupported input, runtime failure, unavailable model, or insufficient confidence produces a typed blocked/abstained result.

The mobile parser distinguishes authorization, integrity, runtime, confirmation, invalid image, crop mismatch, OOD, offline, timeout, throttling, and storage errors.

### Guided multi-image OpenAI comparison

The controlled-testing comparison accepts one to four labelled views such as whole plant, affected leaf, lesion close-up, and leaf underside. The OpenAI key is backend-only.

The prompt is observations-first and permits outcomes including healthy, known disease, abiotic stress, nutrient-related symptoms, pest damage, physical injury, unsupported disease, and insufficient evidence. It forbids pesticide/chemical/brand/dosage/treatment/payment content and returns strict structured JSON.

The deterministic agreement engine does not average conflicting scores:

- compatible classifier and comparison evidence -> cautious likely result;
- conflict or insufficient evidence -> request a specific additional view;
- unsupported/unknown -> no diagnosis and expert-review guidance.

Raw OpenAI text is never rendered directly. Existing classifier, confirmation, capability, role, image safety, and one-time-token gates remain authoritative.

### Accuracy evidence and limits

Do not claim that recent engineering increased accuracy. It made the system measurable and fail-closed.

Known provisional evidence:

- Chilli: provisional public-data result around 97.75% accuracy, macro-F1 around 0.962, 89 samples; not independent multi-farm field proof.
- Redgram: provisional 52-sample result around 86.54% accuracy, macro-F1 around 0.867, coverage around 48%; sterility mosaic recall was weak and leaf spot abstained.
- Banana: a traceable independent held-out field result was not found.
- Paddy/cotton/groundnut: independent field validation remains missing; development-perfect results are not field claims.

General-farmer release requires untouched independent expert-labelled field tests, confidence intervals, critical-class performance, calibration, OOD safety, and no critical slice regression.

## 11. Satellite Stress Alerts

### Foundation

The satellite module contains a provider abstraction, AOI validation, processing engine, persistence, provenance, and mobile states.

AOI rules accept bounded Polygon/MultiPolygon GeoJSON only. Rings, coordinates, size, vertex count, ownership, and structure are validated before provider contact. No boundary is invented from an approximate point.

The Copernicus adapter targets the current Copernicus Data Space STAC service for Sentinel-2 L2A discovery. Credentials remain backend-only. Timeouts, rate limits, malformed responses, missing credentials, no imagery, clouds, acquisition delay, and processing errors map to explicit states.

Production never silently falls back to `MockSatelliteProvider`. Mocks require explicit development/test configuration and are visibly labelled sample data.

### Processing

The pipeline discovers recent scenes, validates acquisition/cloud metadata, selects compatible bands, applies masks, computes existing indices, and emits an alert only with usable AOI coverage. It persists provider/scene ID, acquisition/processing time, AOI hash, processing version, coverage, quality, and provenance.

States include pending, processing, available, no polygon, provider not configured, no imagery, cloud cover, acquisition delay, timeout, rate limited, provider error, and processing error.

No satellite results may be claimed when real credentials/data are unavailable.

## 12. Waterlogging/Flood Alerts

This feature builds on the satellite/geospatial layer but uses a separate evidence contract:

- `CLEAR`
- `POSSIBLE_WATERLOGGING`
- `REVIEW_REQUIRED`
- `INSUFFICIENT_DATA`

Every assessment includes observation time, source, AOI coverage, evidence present/missing, freshness, explanation, baseline scene, provider/scene IDs, hashes, processing version, and decision code.

The default is `INSUFFICIENT_DATA` for invalid/missing AOI, credentials, observations, baseline, freshness, coverage, cloud, provider/processing failure, or conflicting evidence.

NDVI/NDMI alone cannot prove flooding. A cautious possible-waterlogging result requires compatible real imagery and observable surface-water change against a valid baseline. Sentinel-1 SAR support sits behind the provider abstraction where production access permits. Weather, drainage, and elevation are context, not proof.

The feature never claims crop damage, flood depth, field safety, or an irrigation/drainage/evacuation/treatment instruction.

## 13. Nutrient Intelligence

Nutrient Intelligence preserves the existing provider, Gemini integration, corroboration engine, R2 storage, farm context, history, navigation, offline queue, and localization.

The backend validates MIME type, upload size, decoded image, dimensions, corruption, visible plant/leaf evidence, selected crop, farm crop, supported crop, and observed crop compatibility.

Result states include supported finding, possible finding, abstained, invalid image, crop mismatch, unsupported crop, and provider unavailable. Responses expose observed evidence, missing evidence, conflicts, confidence band, abstention reason, next requested evidence, and `expert_verified`.

Provider confidence is observational, not truth probability. The engine does not average conflicting evidence. Low confidence, disagreement, missing corroboration, or disease/abiotic/pest ambiguity causes abstention.

Only allowlisted localized safety guidance is displayed. Raw Gemini text is not rendered. No pesticide/fertilizer brand, dosage, or treatment is generated. `expert_verified` remains false without an actual versioned approval document bound to the policy.

Missing provider credentials in internal/field/production builds return provider unavailable, never mock deficiency data.

## 14. Soil Intelligence and Soil Scan / Smart Sampling

Soil Intelligence separates evidence into:

- measured data, such as farmer-entered or laboratory values;
- imported/document-derived measurements with provenance;
- remotely estimated indicators;
- missing/unavailable inputs.

It never claims that satellite or estimated indicators are laboratory-equivalent soil health measurements.

The provider abstraction can later support accredited labs, government datasets, remote sensing, or Soil Health Card extraction. Unavailable providers return no fabricated values. Farmer-entered values remain labelled as farmer data.

The soil evidence/scan layers record source, measurement/estimate type, timestamps, confidence/uncertainty, provenance, and missing inputs. Terrain and remote sensing remain indicators rather than definitive soil chemistry.

Smart sampling helps organize where samples should be collected from a verified farm geometry. It does not fabricate lab results or convert remote estimates into measured nutrients. Refer to `docs/testing/feature_6a_soil_scan.tdd.md` and backend soil modules for the exact state contracts.

## 15. Crop Calendar

The calendar engine uses a versioned verified-data registry. A schedule/rule pack records canonical crop identity, stages/tasks, region/season scope, source references, reviewer, approval/expiry, version, and hash.

Only active verified packs can generate automated calendar tasks. Unverified, suspended, rejected, expired, or missing packs produce a clear unavailable fallback.

Planting date is farmer-editable. Changing it recomputes future suggestions but does not rewrite confirmed history. Notifications are generated only from eligible verified tasks. Existing localization, offline storage, backend sync, and navigation are preserved.

The calendar cannot invent stage durations or activate unverified crop-stage rules.

## 16. Crop-Stage Tracking

The stage state machine uses:

- `NOT_STARTED`
- `STAGE_UNKNOWN`
- `STAGE_SUGGESTED`
- `AWAITING_CONFIRMATION`
- `CONFIRMED`
- `UNCERTAIN`
- `CORRECTED`
- `COMPLETED`

Stage names come only from an active verified crop-stage registry. Without one, the system may record a farmer-selected stage but cannot generate an automated stage suggestion.

Evidence types remain separate:

- planting-date offset: estimate;
- weather: supporting evidence only;
- growth image/model: supporting evidence only;
- farmer selection: farmer confirmation;
- expert correction: reviewed evidence.

Suggestions never count as confirmed. Farmer confirmation records actor, timestamp, prior/suggested/confirmed stage, registry version, and evidence snapshot. Corrections append history rather than overwriting it. Backward corrections are permitted but explicitly audited.

Optimistic versions and idempotency keys prevent silent last-write-wins behavior. Offline conflicts require reconciliation. Uncertainty suppresses stage-dependent agronomic instructions and automatic notifications.

## 17. Disease-Risk Alerts

The risk-engine framework accepts weather, crop, and confirmed-stage inputs. Agricultural alerts remain inactive without a verified rule pack.

A verified disease-risk pack must include scope, required inputs, source references, reviewer approval, lifecycle status, version, expiry, and hash. Missing/stale/conflicting weather, unconfirmed stage, unsupported crop, or missing pack returns insufficient/unavailable rather than a risk claim.

The framework does not infer disease probability from weather alone and does not generate treatment or pesticide guidance.

## 18. Harvest Readiness

Readiness states include not assessed, insufficient data, not ready, possibly ready, awaiting farmer confirmation, farmer confirmed ready, farmer confirmed not ready, and conflicting evidence.

Only an active verified crop-specific readiness criteria pack can produce `POSSIBLY_READY`. Packs define canonical crop/variety scope, required confirmed stage, observable maturity evidence, dependencies, region/season, references, reviewer, approval/expiry, version, and hash.

Dependencies may include farmer-confirmed crop/stage, farmer planting date, farmer expected date, growth observations, weather provenance, verified calendar data, and suitable recent real satellite evidence. Missing values remain missing; nothing is imputed.

Confidence means evidence completeness/agreement, not harvest certainty. The engine never generates a harvest date. A farmer-entered expected date remains explicitly separate and is never changed automatically.

Farmer ready/not-ready confirmation is audited farmer evidence, not expert verification. It cannot trigger sale, harvesting, irrigation, pesticide, or chemical instructions.

## 19. Action Verification

Action Verification tracks workflow completion only:

`suggested -> viewed -> farmer reported done/not done/deferred -> corrected/cancelled`

Each action records source module/record/version, farm, crop cycle, owner, localized action code, suggestion time, and trusted due/expiry time when supplied.

Farmers can report done, not done, later, or correct a response. Notes are optional. Photos are optional and require explicit retention consent. Server-side upload validation covers MIME, decoded image, size, dimensions, corruption, content hash, protected storage reference, and ownership.

A done response is displayed as “Farmer reported done,” never “verified successful.” The photo is not analyzed to infer recovery or treatment effectiveness.

Outcome tracking is separate: not reported, farmer reports improved/no change/worse, expert review pending, or expert reviewed. Farmer outcomes are subjective evidence. Only authenticated expert review carries an expert marker.

The audit history is append-only with actor, timestamp, prior/new status, request/idempotency identity, source version, and evidence hash. Corrections supersede without deletion. This workflow cannot activate a blocked recommendation from another feature.

## 20. Growth monitoring

Growth monitoring stores farmer observations/images, compares time-based entries, supports stage evidence, and maintains a timeline. Images use protected object storage. Storage failure occurs before report persistence, preventing records that point to fabricated URLs.

Growth observations can support stage/readiness workflows but cannot independently confirm a stage or harvest state.

## 24. Cloudflare R2 object storage

The object storage interface is used by disease controlled reports, nutrient reports, and growth images.

Selection logic:

- complete R2 credentials -> real `R2Client`;
- explicit development/test mock policy -> `MockStorage`;
- otherwise -> `UnavailableStorage` raising `storage_provider_unavailable`.

Production and KVK builds cannot select mock storage. No fake R2 URL is returned when credentials are absent. Disease retention, nutrient, and growth persistence fail before a database record is created with a false URL.
